# Clean-sheet homepage: purge all content, rebuild one showcase page

**Status:** done (2026-09-09) — all 7 tickets closed, code-reviewed, branch `clean-sheet-homepage` pushed to `origin`. See `issues/07-push-and-review.md` for the review findings and their disposition.

## Problem Statement

Pohjola's current front-end content (Home, About, Contact, Posts, Fixtures — every page, every piece of copy in `Data.I18n`) was written early, iteratively, by an agent working inside the framework it was describing. The user wants to find out what the framework's own page-creation pipeline (`make new-feature`, `App.Ui.Templates`, DaisyUI) produces when it is exercised completely fresh, with a blank content slate and no anchoring on anything already written — and to end up with a single, genuinely good homepage that actually sells Pohjola, built the same way any Pohjola user would build a page.

Today the "homepage" is one of five competing, demo-flavored pages (About/Contact/Posts/Fixtures are explicitly demo/placeholder content — Fixtures' own doc-comment calls itself "temporary demo"). None of them were built as a deliberate marketing showcase, and all of them share whatever narrative bias came from being written in the same sitting as the framework itself.

## Solution

Two commits on one new branch:

1. **Purge.** Delete every feature page (`Home`, `About`, `Contact`, `Posts`, `Fixtures`), every route wired to them, every line of their copy in `Data.I18n`, their feature-specific tests, and the one migration that exists only to back the deleted `Posts` feature. Leave the framework kernel untouched — `App.Ui.*`, `App.Layout.*`, `App.Alpine`, `Data.Route`'s machinery, `Data.I18n`'s `Dictionary`/`Lang` machinery, `App.Auth`/`App.Users`/`App.Data.SQL`/`App.Form`/`App.Email`, `Policy.Contract`, the scaffolder itself. This commit is expected to leave the app serving nothing (zero routes) — that's the point, and it's fine for it to be the one commit in this exercise that doesn't need to pass `make check`.
2. **Rebuild.** Resolved decision (this session): not a single page — a small, real site. Four pages, each regenerated via `make new-feature ... WIRE=1 CHROME=1` (this is the mechanism under test): `Home` (hero, pillars, CTA), `About` (framework story/philosophy — reintroduced, but authored fresh, sharing no sentence with the deleted `About`), `Guarantees` (a dedicated page presenting `GUARANTEES.md`'s guarantee table as real site content — Pohjola's most distinctive, checkable claim, and content the old site never had, so it carries zero carryover bias by construction), and `Docs` (an honest "coming soon" stub, not a broken link). A real navbar ties them together: Home | About | Guarantees | Docs (Soon), plus an external GitHub link, alongside the existing language/theme chrome. Content inspired by homepages of comparably-scoped frameworks (Astro, SvelteKit, Phoenix/LiveView, htmx, Elm-lang.org) but not copied from any of them and not reusing a single sentence of any deleted copy. All three languages (`en`/`fr`/`pt`) get real translations, not machine-literal ports of the English.

Both commits land on a single new branch, pushed at the end, followed by `/code-review` against the branch's pre-purge commit (i.e. against current `master`).

## User Stories

1. As the maintainer, I want the purge to be its own commit, so that `git log`/`git show` on that commit is a clean, readable record of everything that was removed.
2. As the maintainer, I want that purge commit isolated to a new branch, so that `master` is untouched and the experiment is fully reversible.
3. As the maintainer, I want the framework kernel (Ui primitives, templates, Alpine, routing machinery, i18n machinery, auth, SQL, forms, the scaffolder) left completely alone by the purge, so that what gets tested is the framework's page-creation capability, not the framework itself.
4. As the maintainer, I want the rebuilt homepage to be generated via `make new-feature`, so that the exercise actually tests Pohjola's own onboarding path (what a brand-new user would run) rather than hand-wiring a route the way the original agent did.
5. As the maintainer, I want the new homepage's copy to share zero sentences with the deleted copy, so that the rebuild is a genuine clean-sheet attempt, not a reword of the old page.
6. As the maintainer, I want the new homepage's content shaped by how comparable frameworks pitch themselves on their own homepages, so that Pohjola's pitch reads like a real framework homepage, not an internal design doc turned into HTML.
7. As a first-time visitor, I want a hero section that states what Pohjola is and who it's for within one screen, so that I can decide in five seconds whether to keep reading.
8. As a first-time visitor, I want to see Pohjola's actual differentiators (compile-time guarantees, Bun-native speed, no-custom-JS Alpine seams) stated as concrete, checkable claims, not marketing adjectives, so that I trust the pitch.
9. As a first-time visitor evaluating frameworks, I want a primary call-to-action (e.g. "View the repository" / "Read the guarantees") and a secondary one, so that I have an obvious next step whichever way I'm leaning.
10. As a first-time visitor, I want to see that documentation is coming rather than a broken link or an empty page, so that the site doesn't look abandoned mid-build.
11. As a francophone or lusophone visitor, I want the French and Portuguese homepage to read as native copy, not a literal translation, so that the site doesn't feel like an English site with a language switch bolted on.
12. As a contributor reading the diff later, I want the new `Home` feature written in idiomatic PureScript (falling back to idiomatic Haskell patterns only where PureScript has no equivalent), so that the rebuild is itself a positive example, not something that needs a follow-up cleanup pass.
13. As a contributor reading the diff later, I want no procedural style (imperative loops, mutable accumulation, stringly-typed branching) in the new code, so that it matches the rest of this FP codebase.
14. As the person running `make gate`/`make test`/`make check`, I want the rebuild commit to pass the full verify ladder, so that the branch is in a real, shippable state once the exercise is done.
15. As the person running the site locally, I want `make dev` to serve a working homepage with DaisyUI styling actually applied (not a bare unstyled page), so that the showcase looks like a finished product, not a wireframe.
16. As the person reviewing this work, I want `/code-review` run against the pre-purge commit once the branch is pushed, so that both axes (does it follow repo standards, does it match this spec) get checked before this becomes anything more than an experiment.
17. As a future agent working on this repo, I want `CLAUDE.md`'s exemplar pointer (`About (static), Posts (data)`) corrected once those pages no longer exist, so that the framework's own navigation pointer doesn't send the next agent to files that aren't there anymore.
18. As the maintainer, I want the routing/i18n/sitemap/template test suites (`RouteSpec`, `ContractSpec`, `TemplateContractSpec`, `ShellSpec`, `PolicySpec`) trimmed to match the new one-route reality rather than deleted wholesale, so that the parts of those suites that are generic over `allRoutes` keep proving what they always proved.
19. As the maintainer, I want the `App.Form`/`App.Email`/honeypot/rate-limit guarantees (`GUARANTEES.md` clauses 13/14) to remain true and tested even though no page currently calls them, so that deleting the `Contact` page doesn't quietly regress a guarantee this repo claims to hold.
20. As the maintainer, I want to know explicitly if any deleted migration (`001_create_posts.sql`) would matter to a real deployed database, so that I don't assume this is risk-free in an environment where migrations were actually applied.
21. As the maintainer, I want `Data.Content` trimmed to only what the new homepage actually references (dropping `Contact`-only constants like `issuesUrl`/`discussionsUrl` if the new page doesn't use them), so that dead constants don't linger as a smaller version of the same bias problem.
22. As the maintainer, I want a brief note on what documentation went stale as a side effect (ADRs/convention docs that use the deleted pages as worked examples), even though fixing them is out of scope for this pass, so that the debt is visible instead of silent.

## Implementation Decisions

- **Branch.** One new branch off current `master` (proposed name: `clean-sheet-homepage`; the developer may rename). Two commits minimum: `purge` and `rebuild` (rebuild may itself be a small number of commits — e.g. scaffold, then content, then i18n — developer's call, as long as the purge stays its own isolated commit first).
- **What "purge" deletes:**
  - `src/App/Features/{Home,About,Contact,Posts,Fixtures}/` — all files, all four dirs plus Home.
  - Every `Route` constructor (`Home`, `About`, `Contact`, `PostList`, `PostDetail`, `Fixtures`) and their entries in `routeCodec` (all three languages), `routeMeta`, `routeTitle`, `allRoutes` in `Data.Route` — `Route` becomes a zero-constructor sum type at the end of this commit.
  - Every corresponding call site in `App.Main` (route dispatch, cache wiring), `App.Layout.Head`, `App.Ui.Templates.SiteShell` (nav rendering), `App.Sitemap`.
  - The full content of `Dictionary`'s `nav`, `hero`, `services`, `cta`, `about`, `contact`, `posts`, `fixtures` fields and their `en`/`fr`/`pt` values in `Data.I18n` — `seo`'s per-page description fields for the deleted pages. What's kept: `Dictionary`'s `footer`, `common`, and a minimal `seo` shape (or an equally-empty placeholder — developer's call on the exact minimal shape, since it will be repopulated in the rebuild commit anyway).
  - `migrations/001_create_posts.sql` (posts-specific; `002`/`003` — sessions/users/OAuth — are untouched, they don't reference posts).
  - Feature-specific tests: `test/PostsSpec.purs` (tests `Posts.Service` directly, which no longer exists) is deleted outright. `test/Route/RouteSpec.purs`, `test/ContractSpec.purs`, `test/TemplateContractSpec.purs`, `test/ShellSpec.purs`, `test/PolicySpec.purs` keep their generic-over-`allRoutes`/`staticRoutes` assertions and drop only the literal per-deleted-route assertions (e.g. `parseRoute ["en","about"]`).
  - `test/FormSpec.purs`, `test/AuthSpec.purs`, `test/UsersSpec.purs` are untouched — they test `App.Form`/`App.Auth`/`App.Users` directly, not through any feature page.
  - `evals/evals/12-add-ui-component/PROMPT.md` references `About`/`Contact` as worked examples inside the eval's prompt text — check whether the eval's `check.sh` assertions actually depend on those pages existing; if so, this eval needs its own fix noted as a follow-up rather than silently left broken.
- **What "purge" does NOT touch (framework kernel, stays exactly as-is):** `App.Ui.*` (Button, Breadcrumbs, Templates/* including `Render`, `SiteShell`'s structural rendering, `Form`, `Hub`, `Article`, `Feed`, etc. — the slot types themselves, not feature call sites), `App.Layout.Page`, `App.Alpine`, `App.Auth`, `App.Users`, `App.Data.SQL`, `App.Data.Fetch`, `App.Form`, `App.Email`, `App.RateLimit`, `Policy.Contract`, `scripts/auto-scaffold.js` and the rest of the scaffolder, `App.Cache`'s machinery (just not any per-route entries tied to deleted routes), migrations `002`/`003`.
- **Rebuild mechanism.** `make new-feature NAME=<Home|About|Guarantees|Docs> TYPE=static WIRE=1 CHROME=1` regenerates each `src/App/Features/<Name>/{Page,View}.purs` and re-wires `Data.Route`/`App.Main`/`Data.I18n` (including nav) scaffolding automatically, run once per page. The generated skeletons are then hand-filled with real content — this is the literal test of the pipeline the user asked for.
- **Site structure (resolved this session).** Four pages, not one: `Home`, `About`, `Guarantees`, `Docs`. Navbar order: Home, About, Guarantees, Docs (labeled as coming-soon/disabled-affordance rather than a dead link), plus an external GitHub link alongside the existing language-switcher/theme-toggle chrome. `Guarantees` is new content (not a resurrection of anything deleted) built directly from `GUARANTEES.md`'s guarantee table — presented as real, checkable claims, matching this session's established "sell it well but be realistic" discipline. `Docs` is a genuine coming-soon page (headline + one-line explanation of what's coming, not a stub with no content at all).
- **Page architecture.** Reuse the existing `Landing` `PageTemplate` (`App.Ui.Templates.Types` — hero slots + a 3-item feature grid + a CTA section) for `Home` if it still fits once re-examined with fresh eyes; `About`/`Guarantees`/`Docs` likely want a simpler content template (see what `TYPE=static` scaffolds by default, and this repo's other static-page conventions) rather than forcing `Landing`'s hero+3-feature shape onto pages that aren't the homepage. A different template shape from what's scaffolded by default is acceptable if the developer judges it doesn't serve a given page well, but should be a deliberate call, not an accident.
- **Content sourcing.** Draw structural/pitch inspiration from public homepages of comparably-scoped frameworks (Astro, SvelteKit, Phoenix/LiveView, htmx, Elm-lang.org, or similar) — structure and tone only, no copied text, no copied visual design. Every factual claim on the page (e.g. "no runtime exceptions past the server boundary," "no custom browser JS") must be checkable against `GUARANTEES.md`/an ADR the way the current hero copy already tries to be — the "sell it well but be realistic" discipline from this session carries forward.
- **DaisyUI.** DaisyUI is already a build dependency (`daisyui@5.7.17` via Tailwind CSS 4) — this is wiring, not new capability. The new homepage should visibly use DaisyUI component classes through the existing `App.Ui` primitive wrappers, not raw utility soup and not hand-rolled CSS.
- **Idiom.** Idiomatic PureScript throughout — no `if`/`then`/`else` where a guarded `case` reads better (see `App.RateLimit` for this repo's established style), `ExceptT`/`liftEither`-style composition over nested cases (see `App.Migration`/`App.Auth`), ADT modeling over stringly-typed branching. Where PureScript genuinely has no idiomatic equivalent (rare, but e.g. some typeclass-hierarchy or laziness idiom), fall back to the equivalent idiomatic Haskell pattern rather than reaching for a procedural shortcut. No mutation, no manual loops.
- **`CLAUDE.md` exemplar line.** `## Task → one doc` currently reads "Exemplars: About (static), Posts (data)." Both are being deleted. Update this one line once the rebuild lands — to `Home (static)` plus whatever the second exemplar becomes, or a note that a data exemplar no longer exists in the tree — since this line actively steers every future agent session.
- **`Data.Content`.** Trim `issuesUrl`/`discussionsUrl` and any other now-orphaned constants if the new homepage doesn't reference them; keep `bookingUrl`/the `Service`/newtype machinery if the new homepage still uses a services/pillars list.

## Testing Decisions

- Good tests here verify externally observable behavior: a route resolves, a page renders through the real layout shell, a guarantee (honeypot, form decoding, route round-trip) holds — never "this exact HTML string appears," which breaks on every copy change.
- `Data.Route`, `Data.I18n` (Dictionary completeness across `en`/`fr`/`pt` is compiler-enforced, not test-enforced — this is `GUARANTEES.md` clause 7 and needs no new test), and `App.Ui.Templates.*` are the modules under direct test change; `App.Features.Home.{Page,View}` gets whatever coverage this repo's existing convention gives a static feature (see `docs/conventions/testing-recipes.md` and the `About` exemplar's own test coverage, before it's deleted, as prior art for what a static page's test shape looks like).
- Prior art for "trim a route-generic test suite instead of deleting it": `test/Route/RouteSpec.purs` and `test/ContractSpec.purs` already iterate `allRoutes`/`staticRoutes` for their bulk assertions — removing the deleted routes' literal per-route assertions and leaving the generic iteration alone is the established shape, not a new pattern.
- `App.Form`'s honeypot/decode guarantees (`GUARANTEES.md` #13/#14) are already tested independently of any feature page (`test/FormSpec.purs` imports `App.Form` directly) — confirm this stays true after the purge; no new test is needed for this, only verification that it wasn't accidentally coupled to `Contact`.
- Full verify ladder from `AGENTS.md`/`CLAUDE.md` applies to the rebuild commit(s): `make gate` (Policy.Contract — no `class_`, FFI allowlist, no unsafe escape hatches), `make test` (Alpine/cache/forms/templates/Main were touched, so this is required, not optional), `make format-check`, `make check` before considering it done. The purge commit itself is explicitly allowed to leave the tree in a non-passing (zero-route) state — see Solution.
- Per `CLAUDE.md`'s UI-change instruction: start `make dev` and view the rebuilt homepage in a browser (all three language paths) before calling this done — type-checking and the test suite verify correctness, not that the page actually looks like a good homepage.

## Out of Scope

- Rewriting prose docs that use the deleted pages as worked examples (`docs/conventions/adding-pages.md`, `data-layer.md`, `design-system.md`, `component-checklist.md`, `generators.md`, `docs/SETUP.md`, `docs/superpowers/specs/2026-08-31-page-architectures.md`, ADR-008, ADR-012, `docs/conventions/server.md`, `docs/conventions/forms.md`) — user said "no docs so far but we'll get to it." Noted as follow-up debt (user story 22), not fixed here. The one exception is the single `CLAUDE.md` exemplar line (see Implementation Decisions) because it actively misdirects future agent sessions, not just a human reader.
- A documentation site or actual docs content — the spec explicitly allows a "coming soon" treatment for docs instead.
- Any change to `App.Auth`/`App.Users`/CSRF (`ADR-005`) work-in-progress — unrelated to this spec, must not regress.
- Reconciling `migrations/001_create_posts.sql`'s deletion against any real, already-migrated database — there is no live database in this environment; if this branch is ever deployed somewhere that already ran migration `001`, that's a real reconciliation problem for whoever deploys it, flagged here rather than solved.
- Fixing `evals/evals/12-add-ui-component`'s `About`/`Contact` reference if its `check.sh` turns out not to actually depend on those pages existing (only revisit this eval if it turns out to be broken by the purge).
- A `Contact`/community page and a `Posts`/blog — deliberately not part of the resolved four-page structure; a GitHub link in the navbar covers the "how do I reach the project" need without resurrecting the old `Contact` page's issues/discussions layout.

## Further Notes

- This is explicitly framed by the user as a test of the framework, not a one-off page build: the deliverable that matters most is proof that `make new-feature` → hand-authored content → `make check` green is a real, followable path for a brand-new Pohjola page, with nothing hidden or hand-waved.
- "No bias from the last page" is a hard constraint on wording, not on architecture — reusing `Landing`'s slot shape (hero/features/CTA) is fine if it's the right shape; reusing any of its sentences is not.
- The purge commit's `git diff`/`git log` output is itself a deliverable the user wants to see ("I want to see the rms on the logs") — favor `git rm` over silent overwrites so the deletions are legible as deletions in the log, not buried inside larger diffs.
- Once the branch is pushed, `/code-review` should run with the fixed point set to the commit immediately before the purge (i.e. current `master` tip, `02ba58e` as of this spec) so the review sees the whole purge+rebuild diff as one unit, checked against both this spec (the Spec axis) and this repo's documented standards plus the Fowler smell baseline (the Standards axis).
